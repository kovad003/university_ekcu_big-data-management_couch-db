# Data dictionary

All data is synthetic: generated by `scripts/lib/data.py` with a fixed seed (42), so every run produces the same 100 orders. The exact sample is committed as `data/orders.json`. Names, cities and streets are invented Hungarian-style values. Emails use the reserved `example.com` domain. No licence or reuse conditions apply.

## Databases

| Database                                      | Where   | Created by                  | Settings                         | Contents                                                             |
|-----------------------------------------------|---------|-----------------------------|----------------------------------|----------------------------------------------------------------------|
| `orders`                                      | A and B | `02_seed.py`                | normal, `n=1`                    | 100 orders loaded into A; B is filled by replication in experiment B |
| `orders_global`                               | A       | `30_partitioned_queries.py` | normal, `n=1`, `q=2`             | the same 100 orders                                                  |
| `orders_partitioned`                          | A       | `30_partitioned_queries.py` | `partitioned=true`, `n=1`, `q=2` | the same 100 orders                                                  |
| `orders_global_big`, `orders_partitioned_big` | A       | `30_… --timing` (optional)  | as above                         | 10,000 orders (seed 7)                                               |
| `txn_test`                                    | A       | `40_atomicity.py`           | normal, `n=1`, no replication    | stock and bulk test documents                                        |
| `_users`, `_replicator`                       | A and B | `01_setup.py`               | system databases, `n=1`          | users; replication job documents                                     |

`n` is the number of copies of each shard; one node can hold only one. `q` is the number of shards. Both partitioned-query databases use the same `q` so that the comparison is fair.

## Order document (`type: "order"`)

| Field                | Type             | Example                     | Meaning and rules                                                                                                    |
|----------------------|------------------|-----------------------------|----------------------------------------------------------------------------------------------------------------------|
| `_id`                | string           | `store01:order001`          | `<tenant>:order<NNN>`. The part before `:` is the partition key in `orders_partitioned`, and always equals `tenant`. |
| `_rev`               | string           | `1-2d37e26a…`               | Set by CouchDB: `<generation>-<hash>`. A new value on every write; an update must send the current one.              |
| `type`               | string           | `order`                     | Document kind. Always `order` here.                                                                                  |
| `tenant`             | string           | `store01`                   | Store that owns the order: `store01` … `store05`. Indexed.                                                           |
| `order_no`           | integer          | `1`                         | Order number within the store, 1–20.                                                                                 |
| `status`             | string           | `open`                      | One of `open`, `paid`, `shipped`, `cancelled`. Indexed.                                                              |
| `customer.name`      | string           | `István Szabó`              | Invented full name.                                                                                                  |
| `customer.email`     | string           | `istvan.szabo1@example.com` | Invented; ASCII form of the name plus the order number.                                                              |
| `items[]`            | array of objects | see below                   | 1–4 line items, embedded so an order is written as one unit.                                                         |
| `items[].sku`        | string           | `SKU-COF-01`                | Product code from an 8-item catalogue.                                                                               |
| `items[].name`       | string           | `Coffee beans 1 kg`         | Product name, copied into the order (a later catalogue change does not rewrite history).                             |
| `items[].qty`        | integer          | `3`                         | 1–3.                                                                                                                 |
| `items[].unit_price` | number           | `18.9`                      | EUR, copied at order time.                                                                                           |
| `total`              | number           | `56.7`                      | EUR; always equals the sum of `qty × unit_price`, rounded to 2 decimals (tested).                                    |
| `currency`           | string           | `EUR`                       | Always `EUR`.                                                                                                        |
| `created_at`         | string           | `2026-09-21T15:36:00Z`      | ISO-8601 UTC, fixed width, so text order equals time order. Between 2026-09-01 and 2026-10-26. Indexed (sort key).   |
| `delivery.city`      | string           | `Budapest`                  | One of 6 Hungarian cities.                                                                                           |
| `delivery.street`    | string           | `Dózsa György út 12.`       | Street and house number.                                                                                             |

Fields added during experiments: `payment` (B, on the paid branch), `note` (B and the cross-replication test orders), and `merge_notes` (B, records how the conflict was merged).

### Distribution in the sample

| Status    |  Orders |
|-----------|--------:|
| open      |      42 |
| shipped   |      30 |
| paid      |      20 |
| cancelled |       8 |
| **total** | **100** |

`store01` has 10 open orders, and 6 of them are over 100 EUR. These are the answers experiments C and A check against.

## Indexes (Mango, type `json`)

| Name                    | Database             | Fields                           | Partitioned | Serves                                                  |
|-------------------------|----------------------|----------------------------------|-------------|---------------------------------------------------------|
| `tenant-status-created` | `orders`             | `tenant`, `status`, `created_at` | no          | “open orders of a store over 100 EUR, newest first” (A) |
| `tenant-status`         | `orders_global`      | `tenant`, `status`               | no (global) | “open orders of one store” via `/_find` (C)             |
| `tenant-status`         | `orders_partitioned` | `tenant`, `status`               | yes         | the same question via `/_partition/<store>/_find` (C)   |

No index answers “open orders of all stores” on `orders_partitioned`. Experiment C5 shows the resulting full scan on purpose.
