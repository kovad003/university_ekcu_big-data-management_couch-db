# Apache CouchDB: replication conflicts, partitioned queries, document-level atomicity

Group project, *Big Data Management and Processing*, NoSQL databases track: **Apache CouchDB 3.5.2**.

Everything runs on one example: orders from five small shops. Two CouchDB instances run side by side in Docker. On them, we show CRUD with revisions and an indexed Mango query, then two-way replication with a forced conflict, a partitioned database next to a normal one, and where CouchDB's transactions end (a stale update gets 409; `_bulk_docs` can half succeed).

Each experiment is a Python script that checks its own results and writes them to `evidence/`. One command runs all of it: `python run.py`.

## 3. Topology

```
 host (your laptop)                           Docker network "couchnet"
 ───────────────────                          ─────────────────────────────────────────────
 scripts ──► 127.0.0.1:5984 ──────────────►   couch-a   (single node, volume couch-a-data, admin_a)
         └─► 127.0.0.1:5985 ──────────────►   couch-b   (single node, volume couch-b-data, admin_b)

 replication (only during experiment B):
   job rep-a-to-b-N  stored in A's _replicator:   http://couch-a:5984/orders ─► http://couch-b:5984/orders
   job rep-b-to-a-N  stored in B's _replicator:   http://couch-b:5984/orders ─► http://couch-a:5984/orders
```

A and B are two separate single-node instances, not a cluster. `01_setup.py` shows it: each node's `/_membership` lists only itself. They have their own volumes and their own admin users (`admin_a`, `admin_b`), and their ports listen on 127.0.0.1 only.

The scripts talk to `127.0.0.1:5984` and `:5985`. Replication jobs can't do that. They run inside a container, where `localhost` is the container itself, so their URLs use the service names `couch-a` and `couch-b`.

Each container is capped at 512 MiB and used about 105 MiB in our run. `01_setup.py` saves a `docker stats` snapshot to `evidence/00_setup/versions.txt`.

### Run it: one command

From the project folder (with the `.venv` active, or any Python 3.9+):

```bash
python run.py
```

The first run writes `.env` with random passwords, pulls `couchdb:3.5.2`, starts both containers, runs the setup checks, loads fresh data and runs experiments A to D. Later runs skip the first two steps.

| Command                             | What it does                                                          |
|-------------------------------------|-----------------------------------------------------------------------|
| `python run.py`                     | everything, unattended                                                |
| `python run.py up`                  | start A and B, run setup, load fresh data                             |
| `python run.py A` / `B` / `C` / `D` | one experiment (`B` resets first automatically)                       |
| `python run.py C --timing`          | experiment C plus the optional timing run (10,000 docs)               |
| `python run.py reset`               | back to the starting state (demo data re-seeded)                      |
| `python run.py status`              | container state, versions, health checks                              |
| `python run.py down`                | stop the containers (data kept)                                       |
| `python run.py wipe`                | **delete containers and all data** (asks first)                       |
| `python run.py test`                | offline reference tests (`pip install -r requirements-dev.txt` first) |
| `python run.py manifest`            | write `MANIFEST.sha256`; add `--check` to verify it                   |

Run from a real terminal, a single experiment stops before each step and waits for Enter. That's what we use for recording. `--auto` runs straight through; `--step` forces the pauses where there's no terminal, e.g. PyCharm's Run button. A non-zero exit code means a check failed, and the output says which.

## 5. Data model (Part 3)

One document per order. Every field, database and index is described in [`DATA_DICTIONARY.md`](DATA_DICTIONARY.md). Sample document (from `data/orders.json`):

```json
{
  "_id": "store01:order001",
  "_rev": "1-2d37e26a73818960522c212db135250b",
  "type": "order",
  "tenant": "store01",
  "order_no": 1,
  "status": "open",
  "customer": { "name": "István Szabó", "email": "istvan.szabo1@example.com" },
  "items": [ { "sku": "SKU-COF-01", "name": "Coffee beans 1 kg", "qty": 3, "unit_price": 18.9 } ],
  "total": 56.7,
  "currency": "EUR",
  "created_at": "2026-09-21T15:36:00Z",
  "delivery": { "city": "Budapest", "street": "Dózsa György út 12." }
}
```

The `_id` is a natural key, `<store>:<order>`, not a UUID. Its prefix is the partition key in `orders_partitioned` and always equals `tenant`. `_rev` is `<generation>-<hash>`; every write makes a new one, and an update has to send the current one.

Values are strings, numbers (`total`, `qty`, `unit_price`), nested objects (`customer`, `delivery`) and one array (`items`). Timestamps are fixed-width ISO-8601 strings, so sorting them as text sorts them by time.

Line items are embedded. An order is read and written as a whole, which fits CouchDB's one-document transaction boundary. Product name and price are copied into each line, so a later price change doesn't rewrite old orders. Stock is kept in separate `stock-<sku>` documents, and experiment D3 shows what that split costs.

Three queries shaped the design:

1. Open orders of one store. This is the common one, and the reason for store-prefixed ids, the partition key and the `[tenant, status]` index.
2. Open orders of a store over 100 EUR, newest first, served by `[tenant, status, created_at]`.
3. Open orders across all stores. That needs a global view (experiment C5).

All indexes are Mango JSON indexes: `tenant-status-created` on `orders`, a global `tenant-status` on `orders_global`, and a partitioned `tenant-status` on `orders_partitioned`. Every database has `n=1`, since there's one node. The two partition-test databases both use `q=2`.

The data is generated with a fixed seed (`scripts/lib/data.py`): 5 stores × 20 orders, of which 42 are open, 30 shipped, 20 paid and 8 cancelled. store01 has 10 open. `--timing` makes a separate set of 10,000.

### A. CRUD + Mango (`10_crud_mango.py`, instance A)

1. Create `store01:order900` and get revision `1-…`.
2. Read it back.
3. Update it with the current `_rev` and get `2-…`, then verify.
4. Delete it with `?rev=` and get tombstone `3-…`. A `GET` then returns `404 deleted`.
5. Run the Mango query "open, store01, total > 100, newest first":
   - `_explain` shows that index `tenant-status-created` was selected
   - the result equals a client-side scan of all documents

### B. Two-way replication and conflict (`20_replication_conflict.py`, A and B)

| Step | Action                                                                                                                   | Expected                                                                                                         |
|------|--------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------|
| B1   | Create `rep-a-to-b-1` on A and `rep-b-to-a-1` on B (`continuous: true`)                                                  | both jobs are `running` in `/_scheduler/docs` with no auth error; B catches up to A's doc count                  |
| B2   | Create `store02:order-from-a` on A, then `store03:order-from-b` on B                                                     | each appears on the other instance                                                                               |
| B3   | Create `store01:order-shared` on A                                                                                       | the same `_rev` on A and B (saved: `shared_doc_common_start.json`)                                               |
| B4   | Delete both job documents using their current `_rev`                                                                     | the jobs disappear from `/_scheduler/jobs`; both instances stay writable                                         |
| B5   | A sets `status: paid`; B changes `delivery.street`, both from the common revision                                        | both writes succeed (HTTP 201) with different `2-…` revisions                                                    |
| B6   | Create `rep-a-to-b-2` and `rep-b-to-a-2`: fresh ids, same settings, no `_rev`                                            | `?conflicts=true` shows the same winner and `_conflicts` on both instances; the loser is readable with `?rev=`   |
| B7   | Merge: a three-way per-field merge against the common start, saved on the **winning** branch; then `DELETE ?rev=<loser>` | both instances have the merged doc (paid **and** new street), no `_conflicts`, the loser in `_deleted_conflicts` |

`replication_jobs.json` keeps the job settings, passwords masked.

### C. Partitioned queries (`30_partitioned_queries.py`, instance A)

`orders_global` and `orders_partitioned` (`partitioned=true`) both have `n=1, q=2` and the same 100 documents. The partitioned one rejects an id without a prefix with HTTP 400.

The selector `{"tenant":"store01","status":"open"}` goes to `POST /orders_global/_find`, which uses the global index, and to `POST /orders_partitioned/_partition/store01/_find`, which uses the partitioned one. Both must return the same ids. That's checked with `limit: 100`, and again by paging through bookmarks 3 at a time until a short page, with the data left untouched in between.

C5 asks a cross-store question of the partitioned database. No index fits, so CouchDB warns and reads every document.

This doesn't show data spread over servers, and it doesn't show a speed-up.

### D. Atomicity (`40_atomicity.py`, instance A, database `txn_test`, no replication)

D1: an update that still carries revision `1-…` gets `409 conflict`. The value from the successful update stays.

D2: one `_bulk_docs` request with a valid update for `bulk-a` and a stale one for `bulk-b`. The response is 201, yet inside it `bulk-a` is OK and `bulk-b` is a conflict. Reading both back confirms it.

D3 is the shop version. "Create order + decrement stock" goes out as one bulk request while the stock revision is stale. The order gets saved and the stock doesn't change.

## 7. Troubleshooting

| Symptom                                          | Cause / fix                                                                                                                 |
|--------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------|
| `not ready after 60s`                            | `docker compose ps`; `docker compose logs couch-a`                                                                          |
| Port already in use                              | change `COUCH_A_PORT` / `COUCH_B_PORT` in `.env`                                                                            |
| Replication job state `crashing`, `unauthorized` | wrong credentials in `.env`, or `.env` edited after the job was created. Run `python run.py wipe`, then `python run.py up`. |
| Replication `db_not_found` / connection refused  | the job uses `localhost`: it must use `couch-a` / `couch-b` (see `.env.example`)                                            |
| `already exists. Run python run.py reset`        | the experiments are designed to start from the documented starting state                                                    |
| Windows: `\r` errors or slow I/O                 | clone inside WSL (`~/`), not under `/mnt/c`                                                                                 |
